## Context

A traject holds a corpus of regulations that people are turning into machine-readable
models. While that work is under way, three questions come up constantly and none of them
can currently be answered without opening files by hand:

- how far along is the translation;
- where does it not hold up;
- what changed since the last time anyone looked.

Numbers that answer parts of this do exist, scattered. `script/cross-law-integriteit.py`
checks binding integrity as a CI gate, but it prints text and exits; it cannot say *which*
article to open. The pipeline mirrors untranslatables into a table during enrichment, but
that table records what an enrichment run found, not what the corpus says today. Nothing
computes coverage at all.

The gap is not a missing report. It is that no single place answers these questions over
the model the engine actually loads, at the level of individual items.

## Decision

Add a corpus analysis capability with three parts.

**A metrics core in the engine** (`packages/engine/src/metrics.rs`) that walks the parsed
regulations the resolver holds and returns three indexes: one row per regulation version,
one per article, one per binding. Headline totals are derived from those indexes.

**A reference date** that selects which version of each regulation counts, using the
resolver's own date-aware selection so the report and an execution agree about which text
applies.

**A page in the editor** behind the `panel.analyse` feature flag, at
`/analyse/:trajectRef`, that renders the report and lets a reader move from any number to
the items behind it and on to the article in the editor.

## Why

### Every metric is a selection, not a scalar

The organising principle:

> A headline number is the length of a filter over an index. The number *is* the list.

This is what makes drilling down possible without a second query, and it removes a class
of bug outright: a count can never disagree with the list it opens, because there is only
one thing. Adding a metric becomes adding a filter rather than adding a tally.

### The numbers come from the model the engine loads

The core does not re-read YAML. It reads the already-parsed structures the resolver
resolves against.

A second reader eventually disagrees with the engine, and a metric that disagrees is worse
than no metric: it grants confidence that something is covered while the engine loads
something else. The sharpest case is a `source:` block placed under `parameters:` instead
of `input:`. `Parameter` has no `source` field, so serde drops it at parse time and the
value silently becomes a plain direct parameter. A naive counter reports a working
cross-law binding that never fires.

### One defect class cannot live here, and that is not a gap

That same example cannot be detected by this core, ever. A defect that consists of the
engine being blind cannot be found by asking the engine. Detection requires reading the
raw document, which is what `script/cross-law-integriteit.py` does.

That script is therefore not a redundant second implementation but the only place the
check can live. The `Misplaced` variant exists in the report so a caller can merge
document-level findings into one list, and the core never produces it.

### Three kinds of content, not two

- **Derived**: computed from the model the engine sees. No human needed.
- **Declared**: a judgement someone recorded, with a class and an owner. Comes from the
  annotation layer (RFC-018).
- **Written**: prose saying what the figures mean. No script makes this, and none should
  try.

A page that only counts is a report. What makes it a validation is that a person says what
it means.

### The declared layer needs no schema change

A tag on a note is already legal: a `TextualBody` with `purpose: tagging`, its value drawn
from `corpus/annotations/_vocabulary/ambiguity.yaml`. RFC-018 Decision 9 deliberately kept
those values out of the JSON Schema enum, so a second axis is a second vocabulary file
rather than a new field. The W3C motivations the schema already allows cover two more
blocks: `questioning` for open legal questions, `editing` for proposed changes.

### Tradeoffs

**The report is computed in the browser today.** Every other aggregate screen in the
editor fetches its figures from an endpoint; this one loads the corpus into the WASM engine
and computes client-side. That is a second pattern for a problem the editor already has a
pattern for, and it repeats the work per visitor. It is tolerable at the current corpus
size and should move server-side before it is not. `editor-api` already holds every parsed
law in `AppState.source_map` and reaches the engine through `regelrecht-corpus`, so this
changes the caller and not the core.

**Untranslatables now have two sources.** The pipeline writes them to a table per
regulation and provider during enrichment; this core counts them from the corpus as it
stands. They agree until someone edits a law by hand. The proposal is that the engine
supplies the count and the table supplies the provenance, but this needs deciding rather
than assuming.

**A reference date makes the page non-reproducible by default.** The report is
deterministic given a date, but the page defaults to today, so it shows something different
each day. A snapshot carries its date explicitly, which is where reproducibility matters.

### Alternatives considered

**Compute in `editor-api` from the start.** Better, and where this should end up. Not done
first because the metrics core had to exist and be trusted before the question of who calls
it was worth answering.

**Extend `script/cross-law-integriteit.py` instead.** It answers "is CI green", not "which
article do I open". Making it produce structured per-item output for a UI would turn it
into the core in a language the editor cannot call.

**Store findings in a new file beside the corpus.** Rejected: it creates a second place
where truth lives, and a finding detaches from the article it is about. The annotation
layer already anchors judgements to text.

### Implementation notes

Determinism is a requirement, not a preference: equal input yields equal output byte for
byte. Every collection is sorted before it is returned and no map iteration order reaches
the result. A reference date that cannot be parsed is treated as no date rather than as an
error, because an inventory without a date is still a useful answer and failing the whole
report over a malformed string would hide it.

A regulation with no version in force on the reference date is reported with the reason the
resolver gave, not dropped. "Not counted" and "fine" must never look the same.

Fixtures are invented throughout: no organisation, statute, amount, person or sector. The
repo corpus is integrity-clean, so the defect classification cannot be proven against it;
the invented fixture is the only place that can happen.

## What exists and what does not

The `implementation` field says *partially implemented*. Concretely:

**Built.** The metrics core with its three indexes and seven defect classes, exposed to the
browser as `corpusMetrics(as_of)`. The reference date selecting versions in force. The
editor page behind the flag, with the tile row, the signal list, the dependency graph, the
defect list and the note layer. Every note and every defect links to its article.

**Not built.** The per-regulation table (coverage, outputs, untranslatables per
regulation). The calculation chain showing each intermediate value with its formula. Owner
and status fields on a declared finding. The list of what deliberately is not covered. The
snapshot file and the revision block comparing it with the previous measurement.

**Blocked.** Comparing model outcomes against outcomes in current practice needs a source
for the practice figures that does not exist yet. Scenario coverage is corpus-derived
rather than engine-derived: scenarios are files beside a law, not part of the model, so
they belong to a separate report a caller merges in.
