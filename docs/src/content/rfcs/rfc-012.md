> **Implementation note.** The channel exists on both schema versions and the engine acts on one of them. Schema v0.6.0 has `markings` and `packages/law-model` parses it, without the engine doing anything with it yet. The four runtime modes (`UntranslatableMode` in `packages/engine/src/types.rs`, covered by `features/untranslatables.feature`) run on `untranslatables` in files at v0.5.x. What execution should do with a marked article is a separate decision that has not been taken; see [RFC-031](/rfcs/rfc-031).

## Context

The engine's operation set is deliberately small: arithmetic, comparison, logical, conditional, and a handful of date operations. It only grows when real legal texts demand a new construct. This RFC is about what should happen at that moment of discovery.

Dutch law regularly uses constructs that fall outside the current operation set. The law-generate process (LLM-driven translation from legal Dutch to machine-readable YAML) has no structured way to handle this. Without an explicit "I can't express this" path, the translator will approximate: flattening tables into fragile IF/cases trees, pre-computing dynamic values, silently omitting inexpressible conditions, or inventing creative encodings that pass validation but misrepresent the law.

We call these constructs **markings**: the law is clear about what it means, and the engine's formal language cannot yet express it. The field carried the name `untranslatables` until schema v0.6.0, borrowed from translation theory, because the law-generate process *is* translation and some things don't cross the boundary between natural language and the engine's operation set. [RFC-031](/rfcs/rfc-031) renamed it and says why.

A marking is a flag on an article that is otherwise worked out. It names the one thing that does not fit and leaves standing everything that does. An article reduced to a marking has lost the logic that was derivable. That is a defect, and it should not be read as a cautious translation.

## Decision

The marking mechanism has three layers: generation-time detection, schema annotation, and engine runtime behavior.

### 1. Generation-time detection

The law-generate skill recognizes when a legal construct cannot be faithfully expressed with the available operations. When this happens, the translator:

1. Adds a `markings` entry to the article's `machine_readable` section (see layer 2)
2. Skips the parts that cannot be expressed, no approximation
3. Generates execution logic for the parts that *are* translatable
4. Reports all markings in the generation summary

The law-reverse-validate skill detects likely workarounds that indicate the translator improvised instead of flagging:

- `IF` with >8 cases (possible inlined bracket table)
- Arithmetic chains that approximate rounding
- Hardcoded values that look like pre-computed aggregations

These are flagged as "possible marking workaround, verify with human."

### 2. Schema annotation

An optional `markings` field on the `machine_readable` section. Everything on it is required except `accepted`:

```yaml
machine_readable:
  markings:
    - about: "afronden op hele euro's"
      reason: "The engine rounds to whole units and statutory rounding runs to the cent, so the amount the article states cannot be produced"
      resolution: operation
      resolved_by: "Add ROUND/CEIL/FLOOR operation to engine"
      target: [toeslagbedrag]
      legal_text_excerpt: "Het bedrag wordt naar boven afgerond op hele euro's"
      accepted: false
  execution:
    # ... execution logic for the parts that ARE translatable
```

`resolution` says what has to change: `operation` where the operation must be built, `model` where the format has no shape for the construct. It names the thing to be added rather than the place it runs, because building an operation reaches past the engine into the schema, the model, the BDD grammar and the frontend. `target` names the values in this article that the marking makes unproducible, and every name it lists must be absent from the article's actions. [RFC-031](/rfcs/rfc-031) has the argument for both fields and for the names, which until schema v0.6.0 were `construct`, `reason`, `suggestion` and `kind`.

The three prose fields are ordered and none of them stands in for another. `about` names the construct in the words of the article, `reason` says why it does not fit in terms of what the format does have, and `resolved_by` names the change that would close the gap. The change follows from the diagnosis and the diagnosis cannot be read back out of the change, which is why v0.6.0 requires both after briefly carrying only the second. RFC-031 has that measurement.

Markings are stored as structured data, so tooling can query them. They survive across generate/validate cycles, show up in the admin dashboard and pipeline, and sit next to the article they apply to.

The `accepted` field (default `false`) indicates whether a human has reviewed and acknowledged the gap. This enables per-article scoping of runtime behavior (see layer 3).

An article with a marking keeps the `execution` logic for the parts that are expressible. Where `target` is empty, all of it: the marking then says the explanation is incomplete and the article executes.

### 3. Engine runtime behavior

The behaviour below is what the engine does today, and it reads `untranslatables` on files at schema v0.5.x. Markings are parsed and not acted on, because what execution should do with a marked article is a decision RFC-031 leaves open. The modes are recorded here because any answer will have to improve on them.

When the engine encounters articles with `untranslatables`, behavior is controlled by the `--untranslatable` flag. The engine always has partial execution logic (generation already excluded the parts it could not express), so the modes control how the engine *treats* that known-incomplete result:

| Mode | Behavior | Use case |
|------|----------|----------|
| `error` (default) | Hard error on any unaccepted untranslatable. Accepted untranslatables execute their partial logic with a trace entry. | CI, production |
| `propagate` | Execute partial logic. Outputs from articles with untranslatables carry an `UNTRANSLATABLE` taint that propagates through downstream operations. | Audit, analysis |
| `warn` | Execute partial logic, log warning in trace. No taint propagation, outputs look normal but the trace shows they're incomplete. | Development, exploration |
| `ignore` | Execute partial logic silently. Only valid for entries with `accepted: true`, unaccepted untranslatables still error. | Human-verified acceptable gaps |

Default is fail-fast. Tolerating gaps requires an explicit opt-in.

The trace records untranslatables regardless of mode; the flag only controls what the engine does with them.

In `propagate` mode, `UNTRANSLATABLE` behaves like `NaN` in floating point: any operation involving an untranslatable input produces an untranslatable output. The result shows which outputs are tainted and which are trustworthy. The trace captures the origin point.

The `accepted` field provides per-article scoping. In `error` mode (default), accepted untranslatables are allowed to execute their partial logic: a human has verified the gap is tolerable. Unaccepted untranslatables always error in `error` and `ignore` modes. This prevents a global bypass: teams cannot set `--untranslatable=ignore` and accidentally suppress newly-discovered gaps.

### Markings against the other channels

A norm whose content is filled by a lower regulation or by implementing policy is an `open_term` under [RFC-003](/rfcs/rfc-003). The language expresses it fine and the content sits elsewhere, so no operation the engine gains will ever resolve it. A value that another law produces is an input with a `source`. Both were being written as markings, which is the measurement [RFC-031](/rfcs/rfc-031) reports.

The dividing question is whether the format can express the construct. Only a marking answers no.

## Why

### Benefits

- Prevents silent divergence between law text and machine-readable interpretation
- Fail-fast default: gaps are never silently ignored in CI or production
- Per-article acceptance prevents global bypass, new markings always surface
- Propagation mode shows which outputs are affected without stopping execution
- Drives the engine roadmap: the corpus tells us which operations to add next
- A flagged gap is better than a plausible-looking wrong answer
- Each layer is independently useful, layer 1 requires no code changes

### Tradeoffs

- **More articles will be incomplete** in the short term, because the translator can no longer paper over gaps
- **Schema change** for layer 2: all tooling must handle the field gracefully, and it has now changed twice
- **Heuristic detection has false positives**: a legitimate 10-case IF is not necessarily a workaround
- **LLM compliance is imperfect**: even with explicit instructions, models may still improvise. The reverse-validate heuristics catch some of this but cannot guarantee detection
- **Propagation adds engine complexity**: a new value type handled in every operation

### Alternatives Considered

**Alternative 1: Expand the operation set preemptively**
- Add operations before they're needed.
- Rejected: violates the principle of minimal, auditable operations. We add operations when concrete legal texts demand them.

**Alternative 2: YAML comments only**
- Flag issues as `# UNTRANSLATABLE: ...` comments, no schema field.
- Rejected as sole mechanism: comments are invisible to tooling, can't be queried, and are easily lost during edits.

**Alternative 3: Fail the entire law**
- Abort generation for the whole file if one article is untranslatable.
- Rejected: most laws have a mix. Partial coverage with clear annotations is more useful than no coverage.

**Alternative 4: Propagate by default**
- Default to propagation, require `--untranslatable=error` for strictness.
- Rejected: silent partial results in production are dangerous. The safe default is fail-fast.

**Alternative 5: Global `ignore` without per-article scoping**
- A single `--untranslatable=ignore` flag that bypasses all untranslatables.
- Rejected: breaks the trust model. A team verifying one gap and setting the flag would unknowingly suppress all future gaps. The `accepted` field provides the needed granularity.

### Implementation Notes

**Layer 1** requires editing the law-generate and law-reverse-validate skill definitions. No code changes.

**Layer 2** requires adding the field to the schema, and updating corpus, admin, and pipeline to parse, display, and track it.

**Layer 3** requires adding an `Untranslatable` variant to the engine's `Value` type, propagation logic in every operation, CLI flag parsing, trace entries, and result distinction between clean and tainted outputs.

Ordering is layer 1 → 2 → 3. Each layer is independently useful.

### History

This RFC was written as *Untranslatables* and describes the channel under the name the schema gave it until v0.6.0. That version renamed the field to `markings`, replaced `construct`, `suggestion` and `kind` with `about`, `resolved_by` and `resolution`, added `target`, and removed `norm_gaps` and `enables` from the schema. `reason` was dropped in that first pass and restored before the version shipped, for the reason RFC-031 records. RFC-031 has the measurement and the argument. The mechanism decided here (flag instead of approximate, with `accepted` as the only escape) survived that consolidation unchanged, which is why this RFC is revised rather than superseded.

Layer 3 has not been revised. It still names `untranslatables`, because that is still what the engine reads.
