## Context

A law reads most of its facts from registers, and a register does not hold a
value for everyone. There is no rent for a homeowner, no partner income for a
single person, no WIA decision for someone who never applied, no permit for a
shop that never asked for one. In the YAML such a fact is an input with
`source: {}` (RFC-007), and whoever supplies the data resolves it. When the
register has nothing, the input is `null`.

Until now the engine had no consistent answer to what happens next. Some
places accepted `null` and others raised an error:

- `EQUALS` and `NOT_EQUALS` compared structurally, so `$huur == null` worked
  and was the idiom laws used to test for a missing value.
- `GREATER_THAN` and the other ordered comparisons rejected a `null` operand as
  a type error, so a law that compared rent against a threshold failed for the
  homeowner instead of concluding the rent clause did not apply.
- `ADD`, `SUBTRACT`, `MULTIPLY`, `DIVIDE`, `MIN` and `MAX` did the same.
- `$beschikking.status` on a `null` record raised `VariableNotFound`.
- A cross-law call whose parameter resolved to `null` (`bsn: $partner_bsn` for
  a person without a partner) executed the other law for nobody and failed
  inside it.
- A cross-law call that did not pass a parameter the target declares failed
  with `VariableNotFound` when the target's article used it, even if the
  output that was asked for never touched that parameter.

RFC-016 already settled one corner: a `FOREACH` over `null` iterates nothing,
and a `filter` that evaluates to `null` propagates `null`. RFC-012 settled the
neighbouring case of an untranslatable value, which taints everything it
touches. Missing register data was the remaining gap, and the migration of the
demo corpus (eighty laws written against a runtime that did treat `null` as
unknown) made every one of the cases above fail on a real persona.

## Decision

The engine treats `null` as **unknown**, and unknown propagates, in exactly
these places:

1. **Ordered comparison with null is null.** `GREATER_THAN`, `LESS_THAN`,
   `GREATER_THAN_OR_EQUAL`, `LESS_THAN_OR_EQUAL` return `null` when either
   operand is `null`. `EQUALS` and `NOT_EQUALS` keep their structural meaning:
   `$x == null` is `true` for a missing value, so a law can still test for
   absence. `IN` keeps its structural meaning.
6. **Logic over unknown is unknown, unless a definitive operand decides.**
   `AND` is `false` when any operand is `false`, otherwise `null` when any
   operand is `null`; `OR` is `true` when any operand is `true`, otherwise
   `null` when any operand is `null`; `NOT null` is `null`. An `IF` whose
   case condition is `null` (and no earlier case matched) is `null`: the
   branch might have applied, so neither its `then` nor a later case nor the
   default may be taken in its place. This is the same shape the
   untranslatable already has in these operations (RFC-012). Without it a
   missing register value would collapse to a confident `false` (`Null` reads
   as `false` in a boolean context) and a blank cell in a data table would
   turn "geen recht op zorgtoeslag" green.
2. **Arithmetic with null is null.** `ADD`, `SUBTRACT`, `MULTIPLY`, `DIVIDE`,
   `MIN` and `MAX` return `null` when any operand is `null`. This is the
   element-wise counterpart of the collection rule in RFC-016.
3. **A property of null is null.** `$record.field` on a `null` record is
   `null`, not an error. An object that exists but lacks the field is still an
   error; the record is there and the law is asking for something it does not
   have.
4. **A cross-law call with a null required parameter is not executed.** When
   a parameter the target declares as required (`required` absent or `true`)
   resolves to `null`, the referenced law is not run and the input resolves to
   `null`. There is nobody to look it up for. An optional parameter
   (`required: false`) that is `null` is passed through; the target said it
   can do without.
5. **An optional parameter the caller does not pass is taken from the
   target's data, else it reads as null.** A parameter the target declares
   with `required: false` and the caller omits is first looked up in the data
   sources bound to the target law, with the parameters that were passed as
   the lookup criteria: an answer the applicant gave that law earlier (the
   terrace size on a permit application, kept as data for the permit law) is
   what a tax law asking for the permit should compute with. When no source
   has it, the parameter is filled with `null` before the call. A required
   parameter is never filled in: leaving it out stays the error it always
   was, so a misspelled key in `parameters:` cannot quietly become an unknown
   outcome. This rule applies to the cross-law path only; a top-level caller
   still supplies what the law declares.

`null` is not an untranslatable (RFC-012). An untranslatable says "the law
says something the engine cannot execute"; `null` says "the register has
nothing for this person". The first taints an outcome; the second is a value
the law itself can reason about.

The trace records each of these decisions (a message on the operation that
went unknown): a comparison or calculation that
went `null` because of a `null` operand, a property read on `null`, and a
cross-law call that was skipped because of a `null` parameter, with the
parameter's name.

## Why

### Benefits

- **A law fails for the person, not for the branch.** The rent clause of a
  benefit does not apply to a homeowner; before this RFC the whole benefit
  failed to compute for them.
- **One idiom for absence.** `EQUALS null` was already how laws tested for a
  missing value. The other operations now agree with it instead of throwing
  first.
- **Cross-law calls model what the caller has.** A tax law that asks a permit
  law for "current permit" does not have the application form the permit law
  also declares. Marking those form fields `required: false` says so in the
  permit law itself, which is where a jurist looks.
- **The `required` flag does work.** It decides both new rules, so a caller
  that forgets a required parameter still gets an error.

### Tradeoffs

- **Errors become unknowns.** A `null` that used to stop the calculation now
  flows into the outcome. A law that never checks for `null` can produce a
  `null` output where it produced an error before. That is by design, but a
  law author has to know it; the conformance suite (bucket B,
  `bdd/conformance/null_semantics.feature`) pins each rule so another engine
  cannot drift.
- **`required` defaults to required.** Existing laws that omit the flag keep
  their strict behaviour on the cross-law path. A law that wants the lenient
  rule has to say `required: false`, which is a change to that law.
- **Two comparisons behave differently.** `EQUALS` answers on `null`, the
  ordered comparisons do not. This is deliberate (absence is a fact you can
  test; "more than nothing" is not) but it is one more thing to know.

### Alternatives Considered

- **Keep throwing, fix the laws.** Every law would wrap every register input in
  an `IF ... == null` guard. The demo corpus shows what that looks like: eighty
  laws, hundreds of guards, and the legal text says none of it.
- **Leave `AND`/`OR`/`NOT`/`IF` as they were.** The first implementation did,
  reasoning that only the places that used to throw needed a rule. Review
  showed the gap: a `null` reaching `AND` reads as `false`, so a missing
  box3 value in `wet_inkomstenbelasting_2001` made `wet_op_de_zorgtoeslag`
  answer "geen recht" where it used to raise a type error. Unknown has to
  stay unknown all the way to the output (rule 6).
- **Treat null as an untranslatable.** Tempting because the machinery exists,
  wrong because the meaning differs: an untranslatable marks a gap in the
  model, a `null` marks a gap in the data, and a law can legitimately branch
  on the second.
- **Fill every unpassed parameter with null.** The first implementation did
  this and ignored `required`. It removed the only runtime guard against a
  misspelled parameter key, and the review caught it before it landed.

## Consequences

- Engine: `packages/engine/src/operations.rs` (comparison, arithmetic and
  the logical operations),
  `context.rs` (property access), `service.rs` (cross-law parameters).
- Conformance: `bdd/conformance/null_semantics.feature` against the synthetic
  laws `test_null_semantics`, `test_null_semantics_bron` and
  `test_null_semantics_strikt`.
- Corpus: laws whose parameters are application-form fields that other laws
  never pass should declare them `required: false`; the demo corpus does.
- Schema: no change. `required` on a parameter already exists; this RFC gives
  it meaning on the cross-law path.
