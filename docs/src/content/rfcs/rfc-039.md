## Context

The engine records how it reached a result. `PathNode` (`packages/engine/src/trace.rs:46`) is a tree of steps, each with a type, a name, a result, and an optional free-text message. It is well tested, it renders as box drawing for the CLI and the TUI, and it already crosses the WebAssembly boundary as a JavaScript object rather than a string.

What it cannot do is say which article a step came from. There is no `article` field, no `law_id`, no `legal_basis`, no URL, and no identifier by which a consumer can name a step. The only place an article number appears is inside a message string written for a terminal. Even the root node is named `"{law_id} ({outputs_label})"` (`packages/engine/src/service.rs:703`), which is the output list, not a provision.

Three consumers now reconstruct legal meaning out of those strings:

- `frontend-demo/src/data/lineage.js:17` runs `/^Resolving from SOURCE ([^:]+):/` over the message to find which organisation supplied a value, so the citizen-facing "Gebruikte gegevens" tree is built by scraping English debug output.
- `frontend/src/lib/traceEdges.js` matches nodes by name and splits `"law#output"` out of `CrossLawReference.name` to work out which law a step is in.
- `frontend/src/components/graph/TraceStepDetail.vue:65` carries a comment explaining that it cannot render units, because the trace spans several laws and has no `type_spec` to read.

`packages/tui/src/views/trace.rs` is a fourth signal. It reimplements the rendering over the tree rather than calling `render_box_drawing()`, because a second consumer wanted the structure and the string would not serve.

No RFC owns any of this. [RFC-013](/rfcs/rfc-013) defines the Execution Receipt and leaves the trace as `"trace": { }` in its example envelope, with one bullet reading "Outputs and trace tree". Its tradeoff section also states that "Trace depth is configurable", which is not the case: `TraceBuilder` offers `new`, `new_untimed` and `disabled`, and nothing between.

Four roadmap work packages already treat the trace as a legal document rather than a debugging aid: rechtsbescherming en de execution trace, the informatiepositie of citizens and entrepreneurs, the lakmoesproef of decisions against a burgerdossier, and the werkwijze of the judiciary. Each asks what a recipient can read out of a trace. None of them can be answered while a step cannot name its provision.

The material is already in scope at evaluation time and never joined. `Article { number, text, url }` (`packages/law-model/src/model.rs:713`) holds the verbatim statute and a link to the official source. `LegalBasis { law_id, article, description }` (`model.rs:24`) holds the authored citation, and the schema's own reference object is richer, carrying `paragraph`, `sentence`, `url` and a Juriconnect identifier. An addressing scheme exists too: `regelrecht://{law_id}/{output}#{field}`, with a parser and a builder in `packages/engine/src/uri.rs`.

## Decision

A trace step gets an address and a citation. Concretely: six optional fields on `PathNode`, plus a `Deserialize` derive and a versioned envelope around the serialized form. Every field is `Option` with `skip_serializing_if`, so no existing consumer breaks, and no node type is added or renamed.

### 1. `node_id`

A stable identifier, derived from the node's position in the tree together with its name. Not a UUID: the same inputs must produce the same identifier on a later run, because a golden fixture pins one and a URL fragment points at one. Unique within a trace, which is an invariant with a test rather than a hope.

This is what lets a consumer name a step. `traceEdges.js` matching on names is not a shortcut, it is the only thing available today, and two steps resolving the same input in different laws are indistinguishable under it.

### 2. `anchor` and `legal_basis`

Both are a `LegalAnchor`: `{law_id, law_uuid, article, paragraph?, sentence?, url?, juriconnect?, valid_from?}`. The shape is deliberately the schema's `legal_basis` reference object, so the two are one type and not two dialects of the same idea.

They answer different questions. `anchor` says where the engine was when it took this step, which the engine always knows. `legal_basis` is the citation the authored YAML element carries, passed through as written. Keeping them apart means a `legal_basis` hung on the wrong provision stays visible instead of being quietly normalised into agreement with the engine.

### 3. `yaml_path`

The path to the element inside the article's `machine_readable`, in the dotted, name-keyed path language the corpus already speaks:

```
articles.2.machine_readable.execution.actions.hoogte_zorgtoeslag.value.values.1
```

Not a JSON Pointer. That language is in use in two places already. `YamlNode.vue` in the demo stamps it on every rendered node as `data-path`, and its `childPath` takes a list item's `output`, `name` or `number` as the label, so an action is addressed as `actions.hoogte_zorgtoeslag` rather than `actions.0`. And `corpus/demo/demo-config.yaml` keys `expanded_paths` on it, with `*` wildcards, to decide per law which lines of a law open by default:

```yaml
  zorgtoeslagwet:
    - articles.*.machine_readable.execution.input.is_verzekerde.source
    - articles.*.machine_readable.execution.actions.voldoet_aan_voorwaarden.value.conditions.0
```

Reusing it means a trace step's address is literally an `expanded_paths` entry, so a viewer can already jump to it, and it survives an edit that inserts an action above the one being addressed. It is also legible: `voldoet_aan_voorwaarden.value.conditions.0` says something to a reader, where `/execution/actions/0/value/conditions/0` does not.

`yaml_path` is the field that pays for the rest. It gives trace to YAML in both directions, and through `legal_basis` and the stand-off notes of [RFC-005](/rfcs/rfc-005) it reaches the statute text as well. It is also the only way to address an anonymous operation node, which has no name and therefore no `regelrecht://` URI.

### 4. `uri`

The `regelrecht://{law_id}/{output}#{field}` address, on nodes that denote a value: `Resolve`, `CrossLawReference`, `Action`, `Cached`, `OpenTermResolution`. Built with the existing `RegelrechtUriBuilder`. No new scheme and no second parser.

### 5. `source` and `type_spec`

`source` is `{kind, provider, scope}`, where `kind` is the resolution kind already in `ResolveType`, `provider` names the registered data source, and `scope` names the law a scoped source was registered for. This is the structured form of what `lineage.js` currently extracts with a regular expression, and it is the field that lets that regular expression be deleted.

`type_spec` sits on the result and carries the unit and precision of [RFC-023](/rfcs/rfc-023). Without it a renderer shows `209692`; with it, the same value reads as an amount in euros. It closes the limitation `TraceStepDetail.vue` documents.

### 6. `Deserialize` on `PathNode`, and a versioned envelope

`PathNode` derives `Serialize` only, so a trace is write-only as far as Rust is concerned. `PathNodeType` and `ResolveType` already derive both. Adding `Deserialize` to the node gives a golden JSON fixture, a round-trip test, and a renderer that can be built and tested against a recorded trace with no engine in the loop.

The serialized form becomes `{"trace_version": 1, "root": {…}}`, with the shape published as `schema/latest/trace-schema.json` alongside the existing `annotation-schema.json`. `ExecutionReceipt` embeds that envelope rather than an inline tree of its own.

### 7. Rust owns the text rendering; the tree is the contract

`render_box_drawing()` stays the canonical text rendering for the CLI, the TUI and the pinned fixtures, and its phrasing stays English. Every other renderer consumes the tree.

`message` stays as well, and is documented as presentational. Parsing it is a defect. That sentence is the point of this RFC as much as any field: three consumers do it today, and each one is a consequence of there being nothing else to read.

### 8. Trace depth stays all or nothing

RFC-013's claim that trace depth is configurable is withdrawn. Folding a subtree is a decision about presentation and belongs with the renderer, which knows how much room it has and who is reading. RFC-013 gets one line in its implementation note pointing here, instead of an engine setting nobody has asked for.

## Why

### Benefits

A step can name its provision, so a trace can be read next to the statute it came from. That is what Awb article 3:46 asks of a motivation and what AERIUS I (ECLI:NL:RVS:2017:1259) means by *inzichtelijk en controleerbaar*. The four roadmap work packages become answerable questions rather than blocked ones.

Four consumers get shorter, not longer. The regular expression in `lineage.js` goes, name matching in `traceEdges.js` becomes an identifier lookup, `TraceStepDetail.vue` can show units, and the TUI can address a node without reconstructing a path.

The addressing is reuse rather than invention. `regelrecht://` exists, the dotted path language exists in two places, and the `legal_basis` reference object exists in the schema. Nothing here asks a reader to learn a new way of pointing at part of a law.

`Deserialize` makes a trace testable as data. A recorded trace becomes a fixture, which is how a web renderer gets built without WebAssembly and how a stored trace can be replayed.

### Tradeoffs

The serialized trace grows. Six fields on every node, with an anchor that repeats the law identifier, is roughly two to three times the JSON for the same evaluation. Traces are produced on request and archived by hash, so this is a cost at the point of archiving rather than in the hot path, but it is real.

Anchors will be sparse at first. `legal_basis` appears in 8 of 34 laws under `corpus/regulation/`, and `explanation` appears nowhere in that directory at all, against 344 occurrences under `corpus/demo/`. A node whose element carries no citation gets no `legal_basis`, and the field is absent rather than filled in with the enclosing article. An honest absence is worth more than an invented anchor, and it makes the corpus gap visible instead of papering over it.

`duration_us` remains structurally absent in the browser. The WebAssembly paths force `TraceBuilder::new_untimed()`, because `Instant::now()` trips RefCell aliasing under wasm-bindgen. This RFC records that so no consumer builds on a field that is only ever populated under the CLI and the TUI.

The `yaml_path` language has a known sharp edge, inherited rather than introduced: a dot inside a label would split one segment into two, so `YamlNode.vue` replaces dots in labels with underscores, and an article numbered `2.34` is addressed as `2_34`. The engine must do the same, and the RFC states it as part of the path grammar rather than leaving it as a detail of one component.

### Alternatives Considered

**Alternative 1: keep reading the messages**

Leave the trace alone and let consumers parse the message strings.

Rejected. Three consumers already do it, one is broken on units, and the format they parse is a terminal rendering that exists to be read by a person. Every change to a phrase is a silent break in a citizen-facing view, and a fourth consumer on the landing page would make the pattern permanent.

**Alternative 2: a separate explanation document**

Have the engine emit an explanation next to the trace, shaped for a reader, and leave the trace as a debugging artifact.

Rejected. Two descriptions of one evaluation have to be kept in agreement, and the second one is derived from the same missing information as the first. The trace is not the wrong shape. It is missing its anchors.

**Alternative 3: an event stream instead of a tree**

Replace the tree with a flat sequence of events carrying explicit parent references.

Rejected. Every consumer wants the tree, including the TUI, which builds its own flattening from it. A flat stream would move that work into four places to save it in none.

**Alternative 4: anchors only in the receipt**

Put the legal anchoring in `ExecutionReceipt` and leave `PathNode` as it is.

Rejected. The receipt does not cross the WebAssembly boundary and is reachable only through the CLI `--receipt` flag, so the browser, which is where a citizen reads an explanation, would see none of it. Per-output provenance in the receipt is also the wrong granularity: it names the article that produced an output, not the provision behind each step that led there.

### Implementation Notes

The anchors are available at all four push sites, so the plumbing is threading the article number and the law uuid through `ResolutionContext` rather than finding new information:

- `packages/engine/src/service.rs:703` pushes the root `Article` node and should name the article.
- `service.rs:1185` and `service.rs:2422` push `CrossLawReference`.
- `service.rs:1422` records an untranslatable, which already formats the article into a message.

`node_id` is assigned on `pop`, not on `push`: the node's position is only final once its children are in place.

Converting the consumers is part of the same work, in this order: `packages/tui/src/views/trace.rs`, `frontend/src/lib/traceEdges.js`, `frontend-demo/src/data/lineage.js` with `SOURCE_RE` deleted, and `TraceStepDetail.vue` for the units.

`render_box_drawing()` must produce byte-identical output afterwards. `packages/engine/tests/trace_integration.rs` pins it against `expected_zorgtoeslag_trace.txt`, and that fixture is the guard against the text rendering drifting while the structure changes underneath it. The structured form gets a fixture of its own next to it.

This RFC does not expose `ExecutionReceipt` across the WebAssembly boundary, add an HTTP execution endpoint, correlate traces across organisations (the `trace_id` of [RFC-009](/rfcs/rfc-009)), give `ExecutionOutcome::Yielded` a trace, or sign a trace. The yielded case is a known gap: staged execution under [RFC-008](/rfcs/rfc-008) returns outputs and pending inputs without a trace, so a decision that unfolds over several stages cannot yet be explained as a whole.
