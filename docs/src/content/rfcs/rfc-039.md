## Context

An engine records how it reached a result, as a tree of steps. A step cannot say which article it came from. There is no article, no law, no citation, no link to the statute, and no address by which anything can name a step.

So consumers reconstruct legal meaning out of the line the trace writes for a terminal:

- `frontend-demo/src/data/lineage.js:17` runs `/^Resolving from SOURCE ([^:]+):/` over it to find which organisation supplied a value, and builds the citizen-facing "Gebruikte gegevens" tree from that.
- `frontend/src/lib/traceEdges.js` matches steps by name and splits `"law#output"` out of a name to work out which law a step is in.
- `frontend/src/components/graph/TraceStepDetail.vue:65` carries a comment saying it cannot render units, because nothing on a step declares one.

`packages/tui/src/views/trace.rs` is the fourth signal: it reimplements the rendering over the tree instead of using the text, because the text would not serve.

The material is in scope at evaluation time and never joined. An article carries its number, its verbatim text and a link to wetten.overheid.nl. The law schema allows a `legal_basis` reference on a field, an action and every operation. An addressing scheme exists in `regelrecht://{law_id}/{output}#{field}`.

No RFC owns any of this. [RFC-013](/rfcs/rfc-013) defines the Execution Receipt and leaves the trace as `"trace": { }` in its envelope example. Four roadmap work packages already treat the trace as a legal document: rechtsbescherming en de execution trace, the informatiepositie of citizens and entrepreneurs, the lakmoesproef of decisions against a burgerdossier, and the werkwijze of the judiciary. None is answerable while a step cannot name its provision.

## Decision

The trace becomes a published document format, `schema/latest/trace-schema.json`, versioned independently of the law schema as the note sidecar already is. What the Rust engine derives its fields from is its own business; the format is what a second engine has to produce.

The document is `{"trace_version": 1, "root": …}`, and a step carries:

| Field | What it denotes |
|---|---|
| `node_id` | Address of the step within this trace: the index chain from the root, `n`, `n0`, `n0.2`. Unique within a trace, identical for the same inputs. |
| `anchor` | Where the engine was. Reported whenever it knows the provision, whatever the document cites. |
| `legal_basis` | The citation the document declares for the element at `yaml_path`, as written. |
| `yaml_path` | Address of the element within the law document. |
| `uri` | Address of the value, as a `regelrecht://` URI. Only on a step that denotes a value. |
| `source` | Where a resolved value came from: kind, provider, and the law a scoped source was registered for. |
| `type_spec` | Unit and precision of the result, so 209692 can be shown as an amount in euros. |

Five things that decision settles beyond the field list.

**`yaml_path` uses the path language the corpus already speaks.** Dotted, and for a list item keyed on its `output`, `name` or `number` rather than its index: `articles.2.machine_readable.execution.actions.hoogte_zorgtoeslag.value.values.1`. `YamlNode` stamps that language on every rendered node as `data-path`, and `expanded_paths` in `demo-config.yaml` keys on it to decide which lines of a law open by default. So a step's address is already an `expanded_paths` entry, it survives an insertion above the element it names, and it reads: `voldoet_aan_voorwaarden.value.conditions.0` says something, `/execution/actions/0/value/conditions/0` does not. It is also the only way to address one branch of a nested operation, which has no name for a URI to use.

**`anchor` and `legal_basis` stay apart.** One is where the engine was, the other is what the document claims. Collapsing them would hide a citation hung on the wrong provision. Absent means the element declares none, which is why `explanation` occurs on a `legal_basis` and never on an `anchor`: an engine has no such note to report.

**`message` is presentational.** It exists to be read by a person, its wording is not a contract, it may be in any language, and parsing it is a defect. Every fact it states is in a field. That sentence is the point of this RFC as much as any field is: three consumers parse it today, and each is a consequence of there being nothing else to read.

**A trace is a document you can read back.** `trace_version` travels inside it, and the format is a schema rather than whatever one engine happens to emit, so a recorded trace is a fixture: a renderer can be built against one with no engine in the loop, and an archived trace stays legible to a later reader.

**Trace depth stays all or nothing.** RFC-013's claim that it is configurable is withdrawn. Folding a subtree is a presentation decision and belongs with whatever is doing the presenting, which knows how much room it has and who is reading.

## Why

### Benefits

A step can name its provision, so a trace can be read beside the statute. That is what Awb article 3:46 asks of a motivation and what AERIUS I (ECLI:NL:RVS:2017:1259) means by *inzichtelijk en controleerbaar*. The four roadmap work packages become answerable.

Four consumers get shorter. The regular expression goes, name matching becomes an address lookup, units can be shown, and the terminal rendering stops being an interface.

A format rather than an engine detail is what [RFC-006](/rfcs/rfc-006) and RFC-013 already argue for elsewhere: the schema is the specification and an engine is one implementation, so a municipality running its own engine can produce a trace a court recognises.

The addressing is reuse. `regelrecht://` exists, the dotted path language is in use in two places, and the anchor is the schema's own reference shape.

### Tradeoffs

**The envelope is a breaking change.** Consumers read the root step directly today; they will read `root` out of a document. That is deliberate, because a trace that travels needs its version inside it, and the same work converts the four consumers anyway. Version 1 is therefore the first version, not a promise about what came before.

The document grows, roughly two to three times, for the same evaluation. Traces are produced on request and archived by hash, so the cost lands at archiving rather than in the hot path.

Anchors will be sparse. The corpus declares a `legal_basis` in 8 of 34 laws under `corpus/regulation/`, with `explanation` nowhere in that directory against 344 occurrences under `corpus/demo/`. A step whose element cites nothing reports nothing rather than borrowing the enclosing article's citation. An honest absence is worth more than an invented anchor, and it leaves the corpus gap visible.

`node_id` addresses a position, not an identity. Two evaluations whose trees differ in shape, because one reused a memoized cross-law result and the other did not, address the same work differently. Stability holds for a trace, which is what a fixture pins and a URL fragment names.

### Alternatives Considered

**Keep reading the message.** Rejected: three consumers already do it, one is broken on units, and the string they parse exists to be read by a person, so every rephrasing is a silent break in a citizen-facing view.

**A separate explanation document.** Rejected: two accounts of one evaluation have to be kept in agreement, and the second is derived from the same missing information as the first. The trace is not the wrong shape, it is missing its anchors.

**An event stream instead of a tree.** Rejected: every consumer wants the tree, the TUI included, so this moves the same work into four places to save it in none.

**Anchors only in the receipt.** Rejected: the receipt does not reach the browser, which is where a citizen reads an explanation, and per-output provenance is the wrong granularity anyway. It names the article that produced an output, not the provision behind each step.

**Put `legal_basis` on the law model.** Rejected for this RFC, which is about the trace document and not about what a model parses. Worth noting for whoever implements it: the citation belongs to the element at `yaml_path`, so an engine can report it from the document it loaded without modelling it.

### Implementation Notes

For the Rust engine specifically, the article and the law are already in hand at the four places a trace step is pushed, so attaching an anchor is threading context rather than finding information. The existing box-drawing rendering stays the canonical text form for the CLI, the TUI and the pinned fixtures, and keeps its current output: `packages/engine/tests/expected_zorgtoeslag_trace.txt` is the guard against the text drifting while the structure changes underneath it.

This RFC does not expose the receipt across the WebAssembly boundary, add an HTTP execution endpoint, correlate traces across organisations (the `trace_id` of [RFC-009](/rfcs/rfc-009)), or sign a trace. Staged execution under [RFC-008](/rfcs/rfc-008) returns outputs and pending inputs with no trace at all, so a decision that unfolds over several stages cannot yet be explained as a whole. That is a known gap, not a decision.
